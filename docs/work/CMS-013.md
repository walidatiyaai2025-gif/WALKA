# CMS-013 — Governed Related Products

Tracking: #354 · Parent roadmap: #278

Stack: CMS-010 / PR #349 -> CMS-011 / PR #351 -> CMS-012 / PR #353 -> CMS-013 / PR #355

## Four delivered tasks

### 1. Safe related-product contract

- Reserved content identity: `pdp.related_products` schema v1.
- Payload contains stable Product IDs only.
- Source relationships are deterministic; authored related-item order is preserved.
- Maximum four related products per source product.
- Self-reference, duplicate sources, duplicate targets and unknown catalog IDs fail closed.
- Public normalization strips unknown/private fields.
- No Product Master facts, ASINs, Pantones, URLs, media paths or commerce destinations are copied into this content family.

### 2. Admin authoring

- Typed `/admin/content/pdp/related-products` editor under existing Content capabilities.
- Existing stable WALKA products are the only selectable relationship members.
- Private draft save with optimistic revision protection.
- Explicit publish gate.
- Immutable revision history and restore into a new private draft; restore never auto-publishes.
- Direct malicious requests containing unknown/self-referencing IDs are rejected server-side.

### 3. Public API

- Additive `GET /api/v1/content/related-products` endpoint.
- Published-only versioned content envelope with revision, publish timestamp, ETag and cache headers.
- Shape is normalized again at delivery.
- Stable product IDs are revalidated against the catalog at delivery; invalid published identity returns `content_invalid` rather than leaking bad data.

### 4. Flutter PDP runtime

- Strict compiled stable-ID parser rejects unknown related-product identities.
- Remote -> revision-aware last-known-good SharedPreferences cache -> bundled fallback.
- Older remote revisions cannot overwrite newer LKG state; divergent same-revision content is rejected.
- Content repository is wired into global startup/content state.
- Related Products render as a compiled PDP merchandising panel after the CMS-012 governed core PDP sections.
- CMS membership/order never supplies a URL or commerce action.
- Cards resolve target metadata through the current visible catalog snapshot; hidden/absent products are dropped.
- Card navigation uses compiled stable-product routes only. Amazon purchase remains the target PDP's existing official handoff.

## Regression coverage

Backend:
- contract normalization and fail-closed invariants;
- Admin authentication, draft, publish, stale write, restore, malicious IDs;
- API unpublished state, schema/envelope, ETag/304, private-field stripping and invalid catalog identity.

Flutter:
- strict parser and bundled contract;
- remote/LKG/bundled repository behavior;
- older and divergent same-revision protection;
- visible-catalog resolution drops absent targets;
- related card invokes compiled product callback only.
