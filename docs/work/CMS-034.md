# CMS-034 — Immutable Media Replacement Audit and Rollback

## Goal

Allow the WALKA owner to replace a currently assigned admitted MediaAsset across governed assignment surfaces while preserving target/order identity and recording immutable before/after history with an explicit owner reason. Rollback restores the exact previous references only when no newer owner edit has touched the affected rows.

## Governed assignment families

CMS-034 operates on the assignment metadata already delivered by prior slices:

- Product gallery rows from CMS-032;
- ProductVariant gallery rows from CMS-032;
- compiled Home/category/editorial surface rows from CMS-033.

It does not create a fourth public media-assignment system and does not mutate media binaries.

## Replacement contract

An effective replacement request requires:

1. source and destination MediaAsset IDs that identify two different assets;
2. both assets still exist;
3. both are `admitted`;
4. both have canonical derivatives;
5. both have the same governed MediaAsset purpose;
6. the source has at least one current assignment;
7. the caller supplies the exact optimistic fingerprint of the source's current ordered assignment snapshot;
8. the destination is not already assigned to any affected target;
9. a bounded owner reason is supplied and persisted in immutable history.

Selecting the already-current source asset is an explicit verified no-op. The service still locks and validates the current asset and exact assignment fingerprint, then returns without changing assignments or creating an audit event. A stale same-asset request is rejected rather than using no-op behavior to bypass concurrency.

For an effective replacement, the transaction locks the two assets and affected assignment rows, verifies the snapshot, then changes only `media_asset_id` on the existing rows. Row IDs, target IDs and positions are preserved.

## Immutable audit history

`media_replacement_events` stores:

- stable ULID event ID;
- operation (`replace` or `rollback`);
- source/destination MediaAsset IDs;
- optional unique `rollback_of_event_id`;
- immutable before/after assignment snapshots;
- SHA-256 fingerprints for both snapshots;
- bounded owner reason;
- actor fingerprint;
- creation timestamp.

The model rejects update/delete operations. A rollback never rewrites or deletes the original replacement event; it creates a new immutable linked event with its own required reason.

## Rollback contract

Rollback is allowed only for an original replacement event that has not already been rolled back.

Before rollback:

- the request fingerprint must equal the recorded post-replacement fingerprint;
- the original source must still be admitted and canonical;
- every affected assignment row ID must still exist with the exact recorded target, position and replacement MediaAsset ID;
- the original source must not already occupy one of those affected targets through another row;
- the owner must provide a bounded rollback reason.

Any intervening reorder/reassignment/delete/recreate blocks rollback. This prevents rollback from overwriting newer owner work.

Rollback never automatically unarchives or re-admits the original media.

## Owner workflow

Protected dashboard workspace:

`/admin/media/replacements`

The owner sees admitted+canonical assets that currently have governed assignments. The current asset is shown explicitly as `CURRENT / NO-OP`; other replacement candidates are restricted to admitted+canonical assets with the same purpose. The page shows current target/position references, optimistic fingerprint, a required reason field for effective owner changes, immutable event history including reasons, and a reasoned rollback action for replacement events that have not already been rolled back.

## Public API boundary

CMS-034 adds no public audit endpoint.

Existing public media endpoints continue to expose only the current assignment state:

- `/api/v1/media/product-galleries`
- `/api/v1/media/surfaces`

Replacement event IDs, before/after snapshots, owner reasons, actor fingerprints, rollback links and replacement fingerprints remain private Admin/audit metadata.

## Guardrails

CMS-034 does not:

- copy, delete or replace source/derivative files;
- mutate lifecycle automatically;
- admit media automatically;
- alter Product Master, ASIN, Pantone, pricing/rating or Amazon destinations;
- add Flutter remote binary loading/caching (CMS-035);
- touch protected `Images/` or `mobile/assets/products/**`;
- claim final five-variant owner visual acceptance or close #230.
