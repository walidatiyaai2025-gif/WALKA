# CMS-040..043 — Information surfaces control plane

Parent roadmap: #278
Issues: #358, #359, #360, #361
Dependency: CMS-014 / PR #357

## Goal

Move the released Account information surfaces from hard-coded owner-changeable copy to the WALKA backend while preserving compiled application behavior, verified product truth and safe external-destination boundaries.

The roadmap already reserves one additive API surface, `GET /api/v1/content/information`. This slice therefore uses one revisioned `information` snapshot with four typed subsections so clients cannot observe partial cross-screen publication.

## CMS-040 — About / Story

- Typed About hero, point-of-view story, value-card copy, design-principle copy and closing copy.
- Released stable value/principle IDs are fixed; Admin edits presentation copy only.
- Product story media and executable layout remain compiled.
- Production Account routes to a CMS-aware V140 composition that reuses the approved V131 visual components.

## CMS-041 — FAQ

- Typed ordered FAQ items with unique stable lowercase IDs.
- 1–12 items, bounded question/answer text.
- Remote content cannot supply widgets, executable behavior or Product Master fields.
- Production FAQ renders the validated published Information snapshot.

## CMS-042 — Support / Contact

- Typed support intro, Amazon-order guidance, email card and destination-card copy.
- Support email must be a valid `@walkastore.com` address.
- Website and Instagram destinations remain compiled approved URLs; the CMS has no URL field.
- Unknown/hostile URL fields are dropped at the public delivery and Flutter parsing boundaries.

## CMS-043 — Legal / Privacy / Terms

- Separate ordered Privacy and Terms documents using stable section IDs, title and body.
- A legal-review notice is mandatory and has no visibility switch.
- No arbitrary URL, HTML or JavaScript fields are accepted or delivered.
- Final jurisdiction-specific legal wording remains subject to human legal review; this CMS controls presentation copy, not legal approval status.

## Shared publication and rollback model

- Existing CMS revision service supplies private draft, optimistic revision protection, immutable history, explicit publish and restore-to-new-draft semantics.
- All four typed Admin tabs share the same `information` revision.
- Publish validates the complete four-section snapshot.
- Public API exposes only the normalized allowlist and one schema/revision envelope.
- Flutter consumes remote -> revision-aware last-known-good cache -> bundled fallback.
- Older remote revisions and divergent same-revision responses cannot replace a valid LKG snapshot.

## Protected boundaries

This slice does not make any of the following CMS-editable:

- Product Master facts or claims;
- stable product/variant identity;
- ASIN or Pantone identity;
- Amazon purchase routing;
- arbitrary website/social destinations;
- HTML/JavaScript/code;
- app permissions or executable navigation;
- production media admission rules.

## Validation

Implementation is code-complete on the feature branch. Exact-head Backend API, Pink Source Contract and Flutter full-test/release gates must be Green before the slice is reported complete.
