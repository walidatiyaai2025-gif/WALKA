### CMS-012A — public contract foundation

Delivered:

- reserved content identity `pdp.layout` / schema v1;
- compiled allowlist of PDP section IDs: gallery, identity, variants, usage, facts, editorial, specifications and Amazon trust;
- deterministic ordered-section payload requiring every supported section exactly once;
- required-visible protection for gallery, identity, variants, verified facts, specifications and Amazon trust;
- only presentation-safe usage/editorial sections may be hidden;
- unknown/duplicate/missing section IDs fail closed;
- non-boolean visibility fails closed;
- unknown private/admin fields are stripped during public normalization;
- additive public endpoint `GET /api/v1/content/pdp-layout`;
- explicit publication requirement, ETag/revision caching and the existing CMS public envelope;
- unit regressions for allowlist/order/visibility/protected-section invariants;
- API regressions for unpublished/typed-versioned/invalid/metadata-stripping behavior.

### CMS-012B — protected Admin + Flutter runtime

Delivered:

- protected typed Admin PDP Layout editor under existing `content.view`, `content.write`, `content.publish` and `content.restore` capability boundaries;
- private draft bootstrap, deterministic 1–8 ordering, optional Usage/Editorial visibility controls and protected required-visible presentation;
- direct/malicious requests cannot hide Gallery, Identity, Variants, Facts, Specifications or Amazon Trust because required visibility is server-derived;
- optimistic revision conflict handling, explicit Publish and immutable-history Restore into a new draft;
- Mobile Content dashboard navigation and typed-editor registry routing for `pdp.layout`;
- Flutter `WalkaPdpLayoutContent` schema validation mirroring the backend allowlist and required-visible contract;
- remote published loader through `WalkaApiClient.fetchPdpLayout()`;
- revision-aware last-known-good SharedPreferences cache;
- repository policy: valid newer remote -> LKG; remote failure -> cache; no cache -> bundled manifest; older/divergent same-revision remote cannot replace LKG;
- `WalkaContentController` state integration and app startup wiring;
- `WalkaPdpBody` consumes governed visible sections in server-defined order;
- bundled manifest preserves the existing production PDP order and spacing when the backend is absent or invalid;
- Lunch Usage remains additionally subject to the product model (`showLunchUsage`) so remote data cannot invent usage content for an incompatible product;
- the official Amazon purchase bar remains outside the CMS-controlled body and is never controlled by `pdp.layout`;
- Flutter regressions cover parser fail-closed behavior, LKG/bundled fallback, stale/divergent revision protection and runtime order/visibility.
