# CMS-021 — Home section blocks, ordering and visibility

Tracking: #294 (parent #278)
Branch: `agent/cms-021-home-layout`

## Goal

Make the released WALKA Home composition backend-configurable without allowing remote arbitrary UI execution. The server controls a typed manifest of **known Flutter components**; Flutter owns the widgets, navigation and runtime behavior.

## Stable section IDs

- `hero` — required and always visible
- `benefits` — optional visibility
- `collection` — required and always visible
- `small_changes` — optional visibility
- `trust` — optional visibility

Every published manifest must contain all five IDs exactly once. Order is configurable; unknown, duplicate or missing IDs fail closed.

## Owner-controlled fields

- section display order
- visibility for optional Benefits, Editorial and Trust modules
- Collection eyebrow/title
- Small Changes editorial title/body

Protected behavior/facts remain outside this surface. Hero copy remains in the typed CMS-020 editor. Product facts, claims, ASIN/Pantone, Amazon destinations, navigation callbacks and arbitrary widget types are not remotely editable here.

## Backend contract

Stable key/type: `home.layout` / `home.layout`, schema version 1.

The typed `/admin/content/home/layout` editor reuses CMS-001 revisions and CMS-002 publication semantics:

1. first open creates a private draft from the bundled current Home layout;
2. save validates unique positions 1–5, required visibility and bounded safe copy;
3. preview shows the intended sequence and hidden modules;
4. publish snapshots the typed manifest;
5. history restore creates a new private draft and never auto-publishes.

Public delivery uses an explicit allowlisted `GET /api/v1/content/home-layout` endpoint with revision/timestamp metadata, ETag/cache headers and re-validation. Unknown extra generic CMS keys are stripped by normalization; invalid published manifests return `503 content_invalid`.

## Flutter resilience contract

Flutter accepts only the five compiled section IDs above. Remote data can reorder/configure/hide known modules but cannot instantiate arbitrary widget classes or executable behavior.

Resolution remains:

1. validated remote published layout;
2. revision-aware last-known-good SharedPreferences snapshot;
3. bundled layout matching the existing released Home.

Older remote revisions and divergent payloads with the same revision cannot replace last-known-good content.

## Validation

Backend coverage:

- protected typed editor + safe first-use manifest
- reorder/hide optional modules and safe copy authoring
- duplicate order rejection
- protected Hero/Collection visibility
- stale write conflict
- restore without auto-publish
- public draft isolation/versioned envelope/ETag
- unknown section fail-closed behavior
- unknown field stripping

Flutter coverage:

- known ordered manifest parser
- unknown/duplicate/hidden-core rejection
- remote/cache/bundled resolution
- older/same-revision divergence protection
- rendered Home order, visibility and dynamic safe copy
- existing compact/adaptive Home regressions remain in the full suite
